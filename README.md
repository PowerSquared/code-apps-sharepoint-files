# code-apps-sharepoint-files

SharePoint file operations for [Power Apps code apps](https://learn.microsoft.com/en-us/power-apps/developer/code-apps/overview).

The services generated by `pa app add data-source` do CRUD on SharePoint **list items** only. They
cannot upload file content — `create` writes a metadata row, not a file — and the Power Apps client
library does not cover document-processing APIs. Microsoft's guidance is to
[write a custom service file](https://learn.microsoft.com/en-us/power-apps/developer/code-apps/how-to/sharepoint-operations)
for this. That is what this package is.

Framework-agnostic: plain TypeScript, no UI dependencies.

## Requirements

**`@microsoft/power-apps` >= 1.3.0.** This is a hard floor, not a preference. Earlier versions have
no `format: 'binary'` handling in the connector executor, so an upload body is `JSON.stringify`d and
the resulting file is corrupt. Verified absent in 1.0.4. It is declared as a peer dependency.

## Install

```bash
npm i github:PowerSquared/code-apps-sharepoint-files#v1.0.0
```

Pin the tag. The package builds itself on install via `prepare`.

## Usage

```ts
import { createSharePointFileService } from 'code-apps-sharepoint-files';
import { dataSourcesInfo } from '../../.power/schemas/appschemas/dataSourcesInfo';

const files = createSharePointFileService({
  dataSourcesInfo,
  dataSourceName: 'propertylistingphotos',
});

const uploaded = await files.uploadFile(file, { folderPath: '/Property Listing Photos' });
// uploaded.Id   → SharePoint file identifier
// uploaded.Path → server-relative path
```

Wrap it in your own module to bind the data source name and folder path once, rather than repeating
them at each call site.

### API

| Method | Connector operation |
|---|---|
| `uploadFile(file, { folderPath, fileName? })` | `CreateFile` |
| `replaceFileContent(fileId, file)` | `UpdateFile` |
| `deleteFile(fileId)` | `DeleteFile` |
| `getFileMetadata(fileId)` | `GetFileMetadata` |
| `getFileContent(fileId)` | `GetFileContent` |

All methods throw on failure rather than returning a result wrapper. `getFileContent` returns a
`Uint8Array`; the rest return `SharePointFile` metadata (or `void` for delete).

`fileName` defaults to `file.name` when a `File` is passed, and is required for a bare `Blob`.

## How it works

`DataClient.executeAsync` dispatches any operation declared in a data source's `apis` map. The CLI
only generates a handful of referenced-entity operations, so this package declares the file
operations in the same shape and registers them:

```ts
CreateFile: {
  path: '/{connectionId}/datasets/{dataset}/files',
  method: 'POST',
  parameters: [
    { name: 'connectionId', in: 'path',  required: true, type: 'string' },
    { name: 'dataset',      in: 'path',  required: true, type: 'string' },
    { name: 'folderPath',   in: 'query', required: true, type: 'string' },
    { name: 'name',         in: 'query', required: true, type: 'string' },
    { name: 'body',         in: 'body',  required: true, type: 'string', format: 'binary' },
  ],
  responseInfo: { '200': { type: 'object' } },
}
```

The client library then resolves the runtime URL, substitutes path placeholders, appends query
parameters, attaches auth, and calls the connector. Nothing is bypassed.

### Things worth knowing

**`connectionId`, `dataset` and `tableName` are synthetic.** The executor fills them from the
connection reference and strips them before matching caller parameters. Never pass them. A useful
consequence: if the data source's dataset is bound to an environment variable with `@envvar:`, these
operations inherit the resolved value automatically.

**Pass the real `dataSourcesInfo`, not a copy.** The library's `PowerDataSourcesInfoProvider` is a
first-call-wins singleton — it keeps whichever object reaches it first and ignores later ones.
`createSharePointFileService` therefore mutates the object you pass. Hand it the same one your
generated services import, and registration works regardless of which service makes the first
request. Nothing in your project's generated files is edited, so this survives
`pa app refresh data-source`.

**Binary bodies are base64 strings.** Handled internally; noted because it is the reason for the
version floor.

**Responses parse only when `responseInfo` is declared.** Without it a JSON response arrives as an
unparsed string. `application/octet-stream` always returns a `Uint8Array` and `image/*` always a
base64 string, regardless.

## Unverified: the operation paths

Microsoft publishes the SharePoint connector's operation IDs and parameter keys but **not** its URL
paths. The paths here follow the connector's documented `/{connectionId}/datasets/{dataset}/...`
convention — the same shape the CLI generates for entity operations — but they are not confirmed
against the connector swagger.

A wrong path surfaces as a 404 from the connector on the first call. Check the request URL in the
browser network tab on first run. If one needs correcting, fix it here and every consuming app picks
it up on the next tag.
